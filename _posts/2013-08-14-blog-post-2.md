# 背景

手机相机传统拍照&视频业务，参考传统安卓相机HAL架构，其上下游各模块如下：

**相机apk -> 相机framework/fwk -> 相机HIDL -> 相机HAL -> 后处理引擎-> 后处理算法**（拍照算法、视频算法等）。


传统相机业务 0层示意图

其中，各领域功能简述为：

1. **HAL**：
   1. 相机生命周期&基本控制
   2. 预览、拍照、录像等请求&流管理
   3. 元数据&静态能力值
   4. 共享内存&Buffer轮转
   5. 3A+isp等
2. **ImageProcessService后处理模块**（与后处理算法同属于HAL进程/CameraDaemon进程）：
   1. 接受HAL传递的ImageBuffer、MetaBuffer、RequestInfo
   2. 决策该模式下的后处理算法链路，运行Raw/Yuv等图像后处理算法
   3. 后处理结果送HAL最终编码到Jpeg/Heif/Mp4/LivePhoto文件。
3. **拍照/视频后处理算法**：以拍照领域的传统RAW域多帧变曝光AI融合算法为例，含：
   1. 前处理（预处理、图像配准）
   2. AI检测&分割
   3. AI网络融合
   4. 离线Raw2Rgb、RGB域处理
   5. 离线Rgb2Yuv、YUV域处理等

典型后处理算法如：

1. AiRaw（raw域多帧融合算法，含MFNR多帧融合降噪、HDR等功能）
2. 美肤（yuv域单帧后处理）
3. 虚化算法（依赖双流/深度图的后处理算法）
4. EIS（视频防抖）算法等

传统的相机拍照视频业务中，拍照[后处理算法](https://zhida.zhihu.com/search?content_id=260819415&content_type=Article&match_order=1&q=%E5%90%8E%E5%A4%84%E7%90%86%E7%AE%97%E6%B3%95&zhida_source=entity)或视频**后处理算法+软件**（上图蓝色区域）**实时运行在用户的拍照或视频录制的过程中**。典型场景如：用户点击拍照，APK下发请求经FWK通过HIDL接口下发给HAL，camera HAL（按照后处理算法需求从zsl队列选择帧序列）出多帧，送给后处理模块，后处理模块调用各类算法进行效果优化，优化后的图像帧送给[图像编码](https://zhida.zhihu.com/search?content_id=260819415&content_type=Article&match_order=1&q=%E5%9B%BE%E5%83%8F%E7%BC%96%E7%A0%81&zhida_source=entity)，最终存入媒体库。

# 问题

由于相机业务场景的不断复杂化、后处理算法种类&模块越来越多、计算量越来越大、 AI模型的愈发复杂；而芯片算力的提升有限（或地缘政治导致最先进的芯片算力制程不可获取/制程回退），**性能问题**成为了制约传统相机拍照视频业务演进的重要瓶颈，对用户的相机体验（**效果规格、成片耗时、Shot2See、连拍、长时录制、功耗散热**等）造成了一系列问题。

优化方案：**后处理模块+后处理算法**（上图蓝色部分）**不依赖实时相机硬件资源**，能否将这一块计算负载从**实时相机阶段**（用户拍照或录像等操作相机时刻）**剥离出来**？

# 方案

采用分段式拍照视频软件架构能有效解决上述问题。


分段式拍照&视频 0层示意图

分段式与传统相机拍照视频业务的主要区别在于：

1. 当使用分段式架构时，用户在使用相机进行拍照或录像时，相机HAL只负责采集原始（多张）RAW图/录制原始mp4文件(此时不运行后处理拍照或视频算法)以及其他辅助参考信息，并将这些内容写入文件系统。此阶段称为**一阶段（实时相机阶段）**；
2. 等到用户退出相机后，相机/手机整机整体负载较低的一些场景时（典型如手机熄屏或手机充电期间，或图库浏览照片/播放视频期间），再在后台运行后处理拍照或视频算法，生成效果优化后的照片/视频/LivePhoto并最终替换图库中的原始文件。此阶段称为**二阶段（离线阶段）**。

分段式架构的本质，是在传统的相机拍照视频加后处理的全流程中间强行插入一个**临时状态文件的序列化加存盘**，将相机的**实时图像采集**跟(不断增长的，不依赖于实时相机硬件的)**后处理软件算法**做了**时域分割**跟**功能解耦**。**实时只采图，闲时跑运算。**

通过上述操作，实现了：

1. 拍照视频后处理算法与相机实时出图的**资源错峰**，降低了**一阶段**（用户强感知阶段）的相机**性能功耗开销**，而通过部署在二阶段（用户不感知阶段）的后处理算法来大幅提升效果。
2. 在二阶段中，由于实现了与相机资源错峰，选取了整机（芯片能力负载）负载较低时刻，且整体处理过程均为**离线处理**不需要考虑实时性（相比而言传统的相机实时预览/录制算法要考虑到实时性，单帧的后处理总时长一般要小于帧长如33毫秒，但在离线的二阶段中无此限制），故可以在此**二阶段部署**（相比于传统拍照视频架构）**更大计算量/更高计算耗时的后处理算法**来实现更好的效果。

最终实现用户**拍照视频体验**与**影像效果**的**协同最优**。

## 分段式拍照

### 一阶段

相机apk -> 相机fwk -> 拍照HIDL -> 相机HAL -> 分段式信息采集存盘模块。

一阶段的变化（相比传统拍照）不大，主要是：

关键模块：**筛选、序列化、异步压缩存盘IO**

1. 参考如下信息，决策要做传统后处理还是分段式后处理：
   1. 相机UI界面拍照&视频模式、分辨率、帧率（视频还需考虑录制时长）等信息
   2. 手机ROM剩余空间 > XX% \* 总ROM空间
   3. 分段式已缓存文件独立占用总空间 < XX GB
2. （在走分段式处理的case下）去掉(所有的)后处理拍照算法模块，
3. 收集（仅后处理模块需要用到的）如下信息：
   1. 后处理算法需要的多张输入RAW图（一般7\~9张，含后处理需要的其他图像buffer）
   2. 随帧的metadata（场景检测、人脸检测、深度、3A&isp、产线等信息）
   3. 各类相机辅助器件gyro&ois&acc&flash&variableAperture的状态信息
   4. CaptureContext（描述一次拍照后处理的上下文的、后续可用于恢复整个离线后处理软件框架的一些状态信息/RuntimeInfo）（2、3、4下文统一用广义的metadata指代）

针对上述信息进行

1. **筛选**：仅挑选运行后处理软件+算法模块需要的状态信息最小子集。以metadata为例，会根据metadata的tagId、sectionName、tagName，选择仅后处理模块需要的字段信息而非全部metadata。
2. 深拷贝（深拷贝后，后续对拷贝内容执行序列化+存盘任务为异步执行，不阻塞当前相机运行）
3. **序列化**（序列化是指将数据结构或对象的状态转换为可以存储（例如，存入文件）或传输（例如，通过网络）的格式的过程，而反序列化则是从这种格式中恢复数据结构和对象的过程）为标准的TLV（Tag（标签）、Length（长度）和 Value（值））格式。
4. 存盘：序列化的结果（按照约定的数据结构排布）保存在（芯片组件下的，如data/vendor/camera/.../）文件系统中，其中：
   1. 存盘文件名仅留uuid(e.g: 20251203101010101010...)无后缀名，防止被手机清理助手等软件扫描到
   2. RAW图（含用户隐私图像信息）最终落盘位置（可能需）考虑隐私保护技术方案（HarmonyOS下存盘路径修改为专用信息加密文件路径）
5. 绑定能表征本次拍照任务的uuid/唯一用户id（如拍照时刻的时间戳精确到ms单位）。
6. 将本次拍照状态（是否为二阶段拍照）及本次uuid上报媒体库，媒体库保存待处理的uuid队列信息。
7. 将一阶段生成的低质量图（zsl选取的单张raw图（一般为传统后处理算法选帧需求中的参考帧），执行raw2yuv后将yuv送上层jpeg/heif编码）送图库存档。

其中：

1. **序列化**：

C++中对象序列化分为2种（本文仅讨论分段式技术所涉及的，序列化&反序列化发生在：同一软件操作系统+硬件平台、同一编程语言版本+编译器+ABI、同一进程内、同一数据结构体版本（不考虑新版本代码读取旧版本数据））：

1. 如仅涉及C++ **POD**（PlainOldData，等价于标准内存布局std::is\_standard\_layout\_v<T> && 可平凡拷贝std::is\_trivially\_copyable\_v<T>）类型的数据序列化较简单，可不依赖三方序列化库，直接(void\*首地址 +sizeof(T))逐字节拷贝/memcpy\_s+写入；

(注：这里未考虑T需满足更严格的std::has\_unique\_object\_representations\_v<T>/T必须具有唯一的对象/内存表示，因为我们的序列化&反序列化结果并不会跨平台、跨编译器或跨运行环境序列化，故不要求序列化后的数据/字节流具有一致性，也不关心C++结构体中填充位/PaddingBits的不确定性)

1. （更常见的）是**非POD**类型数据。需额外通过序列化组件执行序列化。

序列化组件可以通过自行编写C++序列化框架，其实现为针对下面（列举常用的）数据类型判断对应type\_traits并实现该类型序列化功能：

* 1. POD基础类型(或更准确的说仅需满足可平凡拷贝/std::is\_trivially\_copyable\_v<T>)
  2. C++标准库中的std::string，std::pair，std::tuple，STL容器（e.g. std::vector\\std::map\\std::array\\ std::deque\\ std::set, std::stack等常用序列容器+关联容器）
  3. std::shared\_ptr，std::unique\_ptr，android::sp等各类（强引用类型，不含裸指针及std::weak\_ptr等弱引用类型指针）智能指针（以及是否根据RTTI从基类指针中选取真正的运行时派生类型）
  4. std::variant，std::optional等类型
  5. 上述类型的继承&组合形式

也可以引用业界成熟三方库，包括：

* 1. google的protobuf ([https://github.com/protocolbuffers/protobuf](https://github.com/protocolbuffers/protobuf) )
  2. cap'n proto ([https://capnproto.org/](https://capnproto.org/) )
  3. cereal库（[https://github.com/USCiLab/cereal](https://github.com/USCiLab/cereal) C++11 header\_only）——简单轻量，**推荐**。
  4. nolman\_json等方案([https://github.com/nlohmann/json](https://github.com/nlohmann/json) nolman\_json部分可参考： [基于nlohmann\_json开源库的json序列化&反序列化](https://zhuanlan.zhihu.com/p/1903040263120721863) ）。

1. **文件IO**：
   1. 文件的写入如果采用Linux的write() / fwrite()等（同步阻塞的系统调用）方法，则默认是不可并发IO的。
   2. 可考虑使用io\_uring(Linux 内核在 5.1 版本引入的一种通过减少系统调用、支持零拷贝和内核轮询等机制实现高性能异步并发的 I/O 框架，可使用封装的**liburing**辅助库调用**io\_uring**)进行并发IO加速。（参考：[异步文件io框架io\_uring-学习笔记](https://zhuanlan.zhihu.com/p/1903138053830207348)）
2. **文件压缩**：文件写入前可以考虑压缩以节省硬盘空间。针对非图像的C++对象数据，考虑**zlib库**压缩，（参考：[https://android.googlesource.com/platform/external/zlib.git/+/master/zlib.h](https://link.zhihu.com/?target=https%3A//android.googlesource.com/platform/external/zlib.git/%2B/master/zlib.h)）（实测zlib压缩在分段式视频一阶段引入的功耗开销较大，最终（可以考虑）去掉该模块）。

### 二阶段


分段式拍照-1层设计图

图库/媒体库APK -> 图库/媒体库fwk中的**分段式子服务** -> **分段式HIDL** -> **HAL中的分段式框架** -> **离线后处理算法**。

首先需要新增分段式的[**HIDL接口**](https://zhida.zhihu.com/search?content_id=260819415&content_type=Article&match_order=1&q=HIDL%E6%8E%A5%E5%8F%A3&zhida_source=entity)（.hal文件，桥接FWK进程与分段式HAL进程的IDL/接口描述语言，参考：[https://source.android.com/docs/core/architecture/hidl?hl=zh-cn](https://link.zhihu.com/?target=https%3A//source.android.com/docs/core/architecture/hidl%3Fhl%3Dzh-cn)），

（**新增HIDL接口**而不是复用相机已有的HIDL接口的原因是：此HIDL接口仅服务于业分段式处理任务，与相机的业务逻辑无关）


HIDL模块示意图

此HIDL接口的**客户端/client**在系统组件(system.img)的媒体库fwk的分段式子服务中，媒体库进程判断如下：

1. 息屏场景：
   1. 手机充电（充电中则不限累计分段式处理时间，非充电则限制累计（可暂停、恢复）分段式处理时间不超过Xmin）
   2. 息屏
   3. 电量高于XX%
   4. 壳温低于XX℃
   5. 待处理分段式任务队列的状态（如：分段式视频需等待所有分段式拍照任务处理完成才下发）
2. 亮屏场景：在 用户需手动访问照片资源场景之前，如：
   1. 用户进入图库查看照片
   2. （通过各类应用）分享\\上传照片等（受系统拦截能力影响，安卓系统并非100%拦截，部分三方网盘应用分享无法拦截。HarmonyOS可以全量拦截）

基于上述状态判断当前条件满足可以下发分段式任务时，则通过媒体库的FWK中的HIDL接口客户端下发二阶段处理请求。

此HIDL接口的**服务端/service**（.hal接口通过hidl-gen编译器编译生成的C++ Impl）在芯片组件（vendor.img）的分段式框架中，该服务端用于响应上述客户端处理请求。同时满足：

1. 此HAL的分段式框架推荐与传统相机HAL所在的常驻进程**CameraDaemon共进程**，而不要作为独立进程，原因：方便分段式服务复用部分HAL离线功能如离线isp等。（早期分段式框架在高通芯片平台上采用过与CameraDaemon不共进程的独立进程形式，方案更复杂（涉及更多IPC）而无必要）
2. 分段式框架作为独立so编译，被CameraDaemon运行时加载（dlopen），原因：防止CameraHAL编译依赖分段式功能。

分段式框架主要的作用有：

1. 接收HIDL接口传来的各类**处理请求**：
   1. 处理（处理一次分段式拍照或者分段式视频）
   2. 暂停（仅分段式视频支持暂停&恢复，拍照不需要）
   3. 恢复（从上次暂停时已处理完的视频序列帧往下接续处理，实际与1）处理共接口）
   4. 放弃（放弃本次分段式处理，分段式尽快退出，并yield让出相机资源）
   5. 查询（Hal进程重启时检查fwk中缓存的PendingRequests/任务队列中保存的uuid与分段式存盘文件的uuid是否match）
   6. 状态同步（内存ROM变化、相机后处理占用状态）
   7. 删除（用户删除媒体库中图片、视频文件时，fwk的PendingRequests删除该uuid，同时通知分段式HAL同样删除缓存的待处理存盘文件）
   8. 客户端&服务端进程双向死亡监听（客户端或服务端进程死亡时，另一端需要有对应同步机制进行记录、清理资源、触发恢复机制）
2. 整体的任务调度管理（ThreadPool管理异步任务执行，JobQueue管理任务队列及优先级排序）
3. 优先级管理（异步请求处理任务中：一般拍照分段式任务优先于视频分段式任务）
4. CPU**频点调节**：开始执行分段式请求时设置CPU执行频点为高频点以提升处理性能，结束后恢复频点为默认
5. 同步异步执行：HIDL接口一般对调用性能有约束，故一次分段式处理请求一般通过异步回调的HIDL接口返回结果
6. **相机资源互斥**：防止分段式任务与传统相机业务抢占**非共享**的相机软硬件资源，如
   1. 离线isp硬件资源（raw2rgb, rgb2yuv, raw2yuv,HardwareImageRegistration...）
   2. 编解码硬件资源
   3. 不支持多实例的单例软件资源等

互斥可能发生的典型场景如在分段式二阶段处理时，如果用户快速打开相机，本次处理任务需Pause。

（如能确保分段式二阶段与传统相机可(分时)共享所有软硬件资源，则可以不考虑本项）

1. **任务状态机**更新：单个处理请求常见状态如下：
   1. pending 尚未处理
   2. running 处理中
   3. pausing 暂停中
   4. paused 已暂停
   5. aborting 放弃中
   6. aborted 已放弃
   7. success 处理成功
   8. failed 处理失败

需管理等各请求状态及状态切换方程。
分段式任务状态机简单示例

采用状态机管理任务状态的好处：软件系统只考虑合乎设计目标的状态切换，某个任务状态环境下只响应合理的（状态机中明确定义的）外部命令，简化系统设计的同时保证各分支的功能流程及最终结果正确。

1. 超时监控：
   1. HIDL接口要求的性能耗时要求（否则阻塞系统IPC/跨进程通信的性能）
   2. 业务自身（单帧处理时长、单次请求处理时长）的性能耗时要求

（超时监控实现参考：[https://zhuanlan.zhihu.com/p/1930919514746360155](https://zhuanlan.zhihu.com/p/1930919514746360155) ）

当严重超时发生时，服务端可以考虑在超时监控回调/ TimeoutAbortMonitor中调用abort()杀死服务端进程，客户端将通过死亡监听重新拉起服务端进程。

1. 性能内存异常处理&&大数据打点。
2. 将处理结果（uuid+正常结果、各类异常&超时等错误码）通过HIDL(异步回调)接口上报。任务结束后，恢复CPU频点为默认模式。

## 分段式视频

分段式视频与分段式拍照共用一套分段式框架，流程相似，较大的不同点在于：

### 一阶段

分段式视频（相比拍照）在一阶段时的差异点：

1、图像数据是否序列化的选择：

1. **不需要存储、序列化YUV**图像数据，因为原始的YUV数据已经编码进入了图库中的原始（没有经过任何后处理算法的，效果80分的）mp4文件中。通过**编解码**，可以从mp4文件中获得（几乎）原始的YUV420数据。
2. 可能会/可选地存储、序列化若干张RAW图（大小\~MB），这块取决于视频的后处理算法需求：一些视频处理算法可能需要一些参考RAW图才能取得更好的降噪或者去模糊的效果，仅靠YUV图效果无法最优。但这里不可能为每个视频帧都保存RAW否则存储ROM占用/功耗（主要是一阶段视频录制对功耗极为敏感）开销太大，可能**每秒存一/几帧RAW**。
3. 但是需要存储每帧图像数据上的**随帧metadata**，视频帧数比较多时需要严格限制（只存必须存的，一般每帧存几十KB）将存取的随帧metadata数据大小。否则的话同样会导致存储ROM占用/功耗高。

同时，多个（以2min 30fps NonSensorHdr视频文件为例，含**3600帧yuv**）视频帧（相对应的一次分段式拍照只需要存**7\~9张输入RAW图**的metadata数据）的metadata数据一般是通过O\_APPEND/追加的模式持续写入同一文件，此模式下io\_uring需要特殊写法（liburing在O\_APPEND模式下写入时不需要指定偏移量，由内核自动追加）才能支持**O\_APPEND**模式做并发读写。

其他问题

1. 上文涉及到2种时间戳：
   1. 视频编解码系统（MediaCodec）从视频中解码出的yuv图像帧显示时间戳/**PTS**（Presentation Time Stamp/显示时间戳，将压缩帧解码后得到的原始帧的显示时间，指示某一帧（视频帧或音频帧）应该在什么时候被呈现（显示或播放）给用户的时间值，以时间基/time\_base为单位）
   2. 传统相机HAL使用的（附在随帧raw或yuv的metadata上的，HAL通用的ANDROID\_SENSOR\_TIMESTAMP）**图像时间戳**（本质是相机驱动在图像sensor首行曝光结束readout开始/SoF时刻打上的壁钟时间戳，参考：[手机相机sensor曝光示意图](https://zhuanlan.zhihu.com/p/1905190906446979557)）

两者基准不一致，（取决于编解码系统自己的实现，可能）**相差了一个手机系统休眠时间**（该时间差Mono2BootTimeOffset等价于Posix系统中CLOCK\_MONOTONIC（去掉手机休眠时间的单调时钟）与CLOCK\_BOOTTIME（包含手机休眠时间的壁钟）两类时间戳之差，可多次采样求差加权得到），要做对齐（可允许一定误差，如abs(transformed\_pts - image\_sof\_timestamp) < 0.5 \* ANDROID\_SENSOR\_FRAME\_DURATION），不然解码一张yuv图像得到的PTS信息无法映射到该帧在一阶段的存盘文件信息的标识id（后者由HAL的帧图像时间戳指定）。

将一阶段序列化的每帧metadata信息如果随yuv帧一起编码到mp4文件的Metadata Track(metadata编码可采用独立元数据轨/**MetaTrack**（与yuv帧的时间戳精确匹配）)中（而不是单独存盘到文件系统中），可避免上述两类时间戳不匹配的问题（代价：（用户可感知的）mp4文件size变大）。

2、二阶段任务执行时，安卓系统可能**休眠**（休眠时整体软件体系被freeze/冻结了，虽然物理时间在流逝但代码会休眠住（此时软件现场环境上下文是保存完好的），直至解除休眠才开始恢复往下执行），解决方法：

1. 图库进程延时子服务在二阶段任务执行期间持续**持有安卓休眠锁WakeLock**（[https://developer.android.com/develop/background-work/background-tasks/awake/wakelock?hl=zh-cn](https://link.zhihu.com/?target=https%3A//developer.android.com/develop/background-work/background-tasks/awake/wakelock%3Fhl%3Dzh-cn)）阻止系统休眠（PARTIAL\_WAKE\_LOCK类型），等到任务执行结束再释放WakeLock准许系统休眠。
2. 在HAL分段式框架的代码中，如超时监控TimeoutMonitor模块（C++超时代码实现参考：[超时回调的一种C++实现](https://zhuanlan.zhihu.com/p/1930919514746360155) ）要监控一段(不包含休眠时间，只含类似有效cpu运行时间片段的)真实软件执行时间段 是否超时，C++代码中**要使用std::steady\_clock**（跟壁钟无关的，适用于度量有效时间间隔的，且度量间隔会自动减掉休眠时间的 单调时钟），而**不要使用std::system\_clock**(简单的壁钟时间)。（参考：[https://en.cppreference.com/w/cpp/chrono.html](https://link.zhihu.com/?target=https%3A//en.cppreference.com/w/cpp/chrono.html) ）

两个方案中如果做到了1（推荐，阻止休眠）也可以不用关注2。

3、一阶段将原始yuv编码进入80分.mp4，二阶段再从80.mp4中解码出yuv，此时：二阶段解码后得到的yuv相比与一阶段HAL写入的原始yuv有**效果回退**（对视频编解码了解不深，不太懂这个问题在工程维度是否有必要（能否肉眼感知的效果变化）/是否可以/如何能解决，可适当**提高编码Bitrate**缓解（优势：更多的细节、更少的压缩瑕疵（如模糊、色块、噪点）；劣势：mp4文件size变大。需权衡））。

4、序列化时可以合理**选择哪些数据被序列化**，一些全局的/持久的/不变的/已经写入硬件的数据可以不参与序列化（因为后续的二阶段本身也是运行在CameraDaemon进程中，传统实时相机一阶段能够访问的上述数据，在分段式二阶段也可访问到）。如：

1. 如器件\\相机\\软件系统不变属性值，e.g: constexpr常量。
2. metadata中的静态能力值StaticCapability
3. 模组EEPROM/OTP中烧录的相机标定数据

一些后处理业务用不到的子图像Buffer（一般相机中非常多的子图像buffer都会attach其智能指针到主图像sensor raw/yuv buffer上）也不应该序列化。

**5、编解码模块的位置**：（可能）**放在fwk模块**比放在hal模块更合理。

原因：后处理算法并不是都在HAL进程中，在fwk中也部署了一些（跟芯片组件能力无关的，相对简单些的、时序在HAL图像算法之后的）后处理算法（如滤镜、水印、偏安卓图形显示渲染方向、如RGBA域的算法）。如果在HAL就完成了mp4封包再传给fwk，那么fwk的后处理算法（在fwk不二次解码的情况下）就难以生效了。

综上：编解码上移到fwk中（可能）更合理。

6、如果编解码上移到fwk，那么fwk与HAL将不再通过文件句柄fd来跨进程交互数据，而是通过（轮转的）一系列的图像共享内存来交互数据，这种跨进程的多帧共享内存的生产者消费者模型就涉及到安卓通用的**BufferQueue机制**（一种基于状态机管理、Fence 同步和跨进程共享内存的在生产者（Producer）和消费者（Consumer）之间高效安全地传递图形缓冲区的安卓机制）。（BufferQueue参考：[BufferQueue 和 Gralloc | Android Open Source Project](https://link.zhihu.com/?target=https%3A//source.android.google.cn/docs/core/graphics/arch-bq-gralloc%3Fhl%3Dnb) ）

编解码上移fwk时分段式视频1层示意图

此时一种（可能的）分段式相关的fwk-hal交互实现为：

1. fwk通过avcodec的接口获取到它的Surface子对象（**ConsumerSurface**）,将对象的IBufferProducer取出来，放入BufferProducerSequenceable,通过HIDL接口传给HAL
2. HAL（离线图谱OfflineGraphCtrlServer）取出BufferProducerSequenceable中的IBufferProducer,并基于此创建一个Surface子对象（**ProducerSurface**）,生产者ProducerSurface先调用RequstBuffer()申请到一块buffer，
3. HAL将该buffer enque到阻塞队列**IveBufferBlockingQueue**中，分段式视频框架驱动后处理OfflineIps，从阻塞队列中取出buffer，依次运行各yuv域后处理算法，最后一个后处理算法组件执行结束后，通过注册的回调将buffer返回给HAL中OfflineGraphCtrlServer的Sink端。
4. OfflineGraphCtrlServer的Sink端调用FlushBuffer()将buffer返回给**SurfaceBufferQueue**。HAL的FlushBuffer()函数中会跨进程地触发fwk中注册的回调函数OnBufferAvailable()，通知消费者buffer已经被生产者填好数据了。
5. fwk的OnBufferAvailable()（注：avcodec中把这个函数封装成了avcodec自己的OnOutputBufferAvailable(),两者等价)中，将buffer编码封包进mp4，然后release该buffer。
7、广义的分段式视频除了处理mp4文件，还可用于处理**动态照片/**[**LivePhoto**](https://zhida.zhihu.com/search?content_id=260819415&content_type=Article&match_order=1&q=LivePhoto&zhida_source=entity)文件(简单理解为一张**封面照片帧**（此时除了视频编解码，可能额外涉及 **jpeg/heif** 等（sdr/hdr）**图像编解码**，可通过三方库**libjpeg\_turbo**实现。参考：[jpeg&exif&heif-学习笔记](https://zhuanlan.zhihu.com/p/1903049446050203400)）+**几十个视频帧**的组合文件形式)（可能的LivePhoto二阶段后处理算法：LivePhoto视频帧**插帧**、LivePhoto视频帧**EIS防抖**）。

8、当分段式架构尚未完成对照片/视频文件的分段式处理时，如果用户此时进入图库浏览照片文件/播放视频文件时（用户拍完照片/视频立即进入图库查看/播放）：

1. 对于照片，由于单张照片的分段式处理时间较短（CPU提频绑核时约\~s），可以调用分段式（CPU提频到最高）完成单张照片处理，将回显帧替换原始低质量帧，并最终送显给用户，此时用户看到是后处理优化过的图片。
2. 对于视频，由于整个mp4文件的分段式处理完成耗时高（一般约束在视频时长的2倍以内），本文所示方案还无法支持处理后的视频帧及时送视频播放组件显示，此时用户看到的是未经后处理的视频帧。

一种（可能的）优化方案是采用**实时渲染视频帧**的分段式方案：

1. 将图库/媒体库的**视频播放组件接入**（编解码上移framework的）**分段式架构**（播放组件framework中注册+调用分段式HIDL服务），
2. 当播放视频时触发分段式视频处理：此时，由于用户播放视频时可能存在快进、慢放、跳转（Seek）等（打破正常的、顺序的解码和渲染流程）操作，对分段式后处理单帧/整体性能耗时就有严格约束了，也仅支持单帧YUV（而非多帧融合）的后处理算法）
3. 将分段式处理的帧实时送给播放组件送显，确保用户看到的是经过后处理的优化帧。

如何在实时渲染视频帧的分段式方案中，同时**兼顾用户播放体验+最终处理视频效果**（后者要求部署更复杂（多帧融合的、单帧计算量较大无法确保实时性的）的二阶段后处理算法），还需考虑更多设计细节。

9、视频封面帧yuv图像（一阶段录制时）需考虑运行后处理算法后再上报。

10、（如果需要）在**非安卓操作系统**（e.g: HarmonyOS）实现上述分段式框架，一些依赖安卓基础组件的模块需要与**安卓解耦**，采用对应操作系统下的自研组件，包括：

## 云拍照&云视频

其软件架构与分段式的几乎一致。以分段式拍照与云拍照举例。

两者在一阶段所做的事情几乎一致（序列化+存盘）。区别主要在于二阶段。

1. 分段式的二阶段处理还是运行在**手机硬件/安卓软件**系统中，
2. 云拍照则是把一阶段的数据（在网络支持的情况下）上传到云端，在**云端**（**更充裕的软硬件环境**下）进行二阶段处理，处理后再下载回手机端侧

云拍照的优势：云端的ai模型算力可以远远超越手机端侧的ai模型，取得更好的优化效果，但实时性略差。

云与分段式不冲突，可以**端云协同**。

# 总结展望

1. 从**传统后处理 -> 分段式后处理 -> 云后处理**，其本质是（不依赖实时相机资源的）相机后处理复杂运算从 **端侧实时 -> 端侧离线 -> 云侧离线** 的**计算运行环境迁移**，从而提供更优的用户实时相机体验+最终影像效果。
2. 分段式架构（最大限度地）保留了**离线后处理所需的数据&运行时环境**，为上述计算迁移提供了可能性。
3. 图库编辑创作（用户手动的、编辑意图显著的对媒体库文件编辑创作并调用后处理算法）与分段式框架（不需要用户手动参与、用户无感知的通用离线后处理算法优化）整体软件架构有相似/共同之处，**图库编辑创作**（是否能）借助/**复用（部分）分段式架构**能够实现更多的功能。
4. 分段式拍照+视频需要在一阶段缓存大容量文件，单次拍照/视频对应多帧RAW/多帧YUV+ metadata等信息，在尽可能保留有效数据的同时减少落盘文件的size，对于分段式及云（数据需通过网络上传云端）拍照视频都很重要。

其中：YUV通过MediaCodec编解码压缩，metadata等非图像信息通过zlib压缩，但对于**RAW数据是否有合理压缩方案**可供分段式使用待完善。
